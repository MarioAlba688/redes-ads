# Redes

Panel web para manejar cuentas publicitarias y redes sociales de un negocio, con IA para publicar. Next.js 16 (App Router) + Prisma 7 + MySQL 8 + Tailwind 4. La interfaz y los textos de usuario van en **español**. Plan por fases en [README.md](README.md); hechas la Fase 1 (login, equipo, roles), la Fase 2 (Meta: conexión OAuth, sincronización de anuncios, pantalla Anuncios) y la Fase 3 (marcas, generador con Claude, borradores, aprobación, programación, publicación en Facebook/Instagram con proceso en segundo plano, calendario). La Fase 4 (Google Ads y TikTok Ads: conexión OAuth y métricas de anuncios, junto a Meta en Anuncios) está hecha con servidores simulados. Siguen LinkedIn (5) y piloto automático/alertas/reportes/despliegue (6); la publicación orgánica en TikTok quedó fuera (exige auditoría de TikTok y soporte de video).

## Decisiones que no son obvias

- **`cacheComponents` está apagado a propósito** (`next.config.ts`). La sesión se valida en MySQL en cada petición para que desactivar a alguien o cambiarle el rol surta efecto al instante. No lo actives ni uses `use cache` sobre datos del usuario o de sesión.
- **Sesiones en BD con token opaco**: la cookie lleva un token aleatorio y la tabla `Session` guarda solo su SHA-256 (`src/lib/auth/session.ts`). `src/proxy.ts` solo mira si existe la cookie; la validación real está en `requireUser()` (páginas) y `authorize()` (Server Actions) de `src/lib/auth/dal.ts`. Los layouts no bastan como barrera: cada página y cada acción debe llamarlas.
- **Permisos**: una sola matriz en `src/lib/permissions.ts`. Ocultar un botón no protege nada; la acción en el servidor siempre re-verifica.
- **React 19 vacía los formularios tras cada envío** (`<form action>`), también con errores. Dos reglas según el caso: (1) formularios simples con campos sin estado propio: las acciones devuelven `values` (`formValues()` en `src/lib/form-state.ts`) y los inputs usan `defaultValue={state?.values?.x}`; nunca devolver contraseñas. (2) formularios con campos **controlados por estado de React** (selects, checkboxes, textareas con `value`): el reinicio los deja en su valor HTML inicial sin que el estado se entere (un select volvía a su primera opción y la siguiente invitación salía con el rol más alto sin que nadie lo eligiera). Ahí se envía a mano: `onSubmit` con `preventDefault()` + `startTransition(() => action(new FormData(form)))` y el estado `pending` de `useActionState` (ver `composer.tsx` y `InviteForm`). Un `key` que remonta el formulario tras guardar borra su `useActionState` y con él el aviso de éxito.
- **Prisma 7**: el cliente se genera en `src/generated/prisma` (ignorado por git; lo regenera `postinstall`) y se conecta con `@prisma/adapter-mariadb` (`src/lib/db.ts`). `mariadb` está forzado a 3.5.4 vía `overrides` porque la 3.4.5 que trae el adaptador tiene avisos de seguridad.
- **Tokens de Meta/Google/TikTok/LinkedIn**: se guardan con `encryptSecret()` (AES-256-GCM, `src/lib/crypto.ts`) y nunca se seleccionan en consultas que alimentan páginas (ver `select` en `cuentas/page.tsx`).
- **Windows / PowerShell 5.1**: `Set-Content -Encoding utf8` añade BOM y rompe `.env` y `package.json`, y `Get-Content` sin `-Encoding` lee UTF-8 como ANSI y **estropea los acentos** de cualquier archivo que reescribas. Edita archivos solo con las herramientas Edit/Write, nunca con `Get-Content | Set-Content`.
- Los avisos de `npm audit` que quedan (`braces`, `deepmerge-ts`, `mysql2`) están en el CLI de eslint/prisma, no en el runtime. No uses `npm audit fix --force`: baja Next y Prisma de versión.

- **La base de datos de producción está en un VPS** (MySQL 9.7, base `db-redes`; host y puerto en `.env`, no se repiten aquí). El mismo servidor MySQL aloja otras bases y usuarios de otros proyectos, y la app todavía se conecta como `root`: crear un usuario `redes_app` limitado a `db-redes` es prioritario. `DATABASE_URL` en `.env` apunta ahí; la clave la pone el usuario a mano, nunca se pide ni se pega en el chat. Desde un PC la latencia medida es ~380 ms por consulta, así que la app debería correr en el mismo VPS. TLS por `?sslaccept=…&sslcert=…` (`src/lib/db-config.ts`, la misma URL la entiende el CLI de Prisma). **Contra esa base solo `npm run db:deploy`**: nunca `db:migrate` / `prisma migrate dev|reset` (pueden borrar datos). Las migraciones nuevas se crean contra una base local desechable y luego se despliegan. Antes de aplicar migraciones al VPS, confirmar con el usuario que `db-redes` está vacía o es solo de esta app.

- **Meta (`src/lib/meta/`, `src/app/api/meta/`)**: Graph API v26.0. Flujo: `/api/meta/connect` (cookie `state` de un solo uso) → Facebook → `/api/meta/callback` (código → token corto → token largo ~60 días → descubrir cuentas/páginas/Instagram → guardar cifrado; primer sync de 90 días con `after()`). Todas las llamadas llevan `appsecret_proof`; los tokens van en la query, así que **nunca se registran URLs ni mensajes de error de `fetch`** (`graph.ts` los reemplaza por un `MetaApiError` seguro). La paginación usa el cursor `after`, no `paging.next`. Un token vencido (código 190) deja la cuenta en `EXPIRED`; límites de uso o errores de red solo guardan `lastError`. `AdInsightDaily` se reemplaza por ventana (`replaceInsights`), no se acumula. Se piden de una vez los permisos de publicación y métricas orgánicas (lista por defecto en `config.ts`) para no obligar a reconectar en la Fase 3, pero `META_SCOPES` en `.env` los sobreescribe: Facebook rechaza con "Invalid Scopes" (en modo desarrollo) los permisos que la app de Meta no incluye, y la app del usuario empezó solo con el caso de uso de anuncios (Marketing API), sin los de páginas/Instagram. Sin permisos de Instagram, `discover.ts` ya cae a listar solo páginas.
- **Pruebas de Meta sin credenciales**: `e2e/fake-meta.mjs` imita a Meta (OAuth, cuentas, insights y, desde la Fase 3, publicación: feed, fotos multipart, contenedores de Instagram, con escenarios de fallo `publishFail`/`flaky`/`igContainer`); la app lo usa con `META_API_BASE_URL` (solo acepta localhost). `npm run test:e2e:meta` arranca app + servidor falso y vacía la base `*_test`. Cualquier cambio en el flujo de Meta debe mantenerlo en verde. La conexión OAuth ya se probó con la app de Meta real del usuario; la publicación real aún no (su app no tiene los casos de uso de páginas/Instagram).
- **Manual de Facebook/Instagram dentro de la app** (`src/app/(app)/manual/`, `src/lib/meta/diagnostics.ts`): página `/manual` para cualquier rol con `requireUser()`; menú «Manual» en `app-shell.tsx`. El texto vive en `page.tsx` (piezas en `parts.tsx`: `Section`, `Steps`, `Code` con `CopyButton`, `Callout`, `Problem`) y la dirección de retorno OAuth sale de `APP_URL` en cada render. El recuadro **«Tu estado ahora»** solo lo ve quien tiene `accounts.manage`: `buildMetaDiagnostics()` es una función pura (probada en `tests/meta-diagnostics.test.ts`) que recibe lo que la página lee de `env()`, de la lista efectiva de `META_SCOPES` y de `SocialAccount` (`kind,name,scopes`; nunca tokens) y devuelve avisos `ok|warn|todo` con el ancla del paso que lo arregla. `publicImageCheck()` detecta `APP_URL` local o sin HTTPS y también direcciones de ejemplo copiadas tal cual (`palabras-al-azar`, `tu-direccion`, `example`…): ya pasó que alguien pegó un ejemplo del chat en `MEDIA_PUBLIC_BASE_URL`. **Si cambias un mensaje de error de Meta o del flujo de publicación, actualiza también su entrada en «Mensajes frecuentes»** (`#problemas`) y mantén las anclas (`#permisos`, `#problemas`, `#publicar-instagram`…), porque Cuentas y la ficha de una publicación enlazan a ellas. Cubierto en la sección 14 de `e2e/meta.e2e.mjs` y en `e2e/pipeline.e2e.mjs`.
- **Anuncios creados desde la app** (`src/lib/promotions/`, `src/lib/meta/marketing.ts`, `src/app/(app)/anuncios/{creados,nuevo,campanas}`, `src/app/api/ads/search`, tabla `AdPromotion`, columna `SocialAccount.dailyBudgetCap`, migración `ad_promotions`): **gasta dinero real; las protecciones son lo primero**. (1) **Moneda**: Meta no recibe pesos/dólares sino la unidad mínima, con un "offset" propio por moneda (**COP = 1, USD = 100**, tabla oficial en `currency.ts`, consultada el 2026-10-16). **Nunca derives la unidad mínima de `Intl` ni de ISO 4217** (ISO le da 2 decimales al COP: sería 100× el gasto); una moneda fuera de la tabla se rechaza. `parseBudgetInput` es estricto a propósito («50.000» en COP = cincuenta mil; en USD es ambiguo y se rechaza). (2) **Todo se crea PAUSADO** (campaña, conjunto, anuncio) y `createPromotion` lo **verifica contra Meta** (presupuesto leído = pedido, los tres en `PAUSED`); si no cuadra o algo falla a medias, `rollback` pone `DELETED` (hijos primero) y la fila queda `FAILED`. (3) **Tope diario**: `SocialAccount.dailyBudgetCap` lo fija el administrador; sin tope no se crea ni se activa; **tope mensual** opcional (`monthlyBudgetCap`, `monthly.ts` puro y `monthlyCapProblem`/`enforceMonthlyCaps` en `service.ts`): al activar proyecta, por cada mes que toque el anuncio, `gastado en el mes (AdInsightDaily, se vuelve a descargar con syncAdAccount si tiene >60 min; si no se puede y el dato tiene >24 h, bloquea) + lo que pueden gastar los otros ACTIVE de la app + lo de este` contra el tope (también al subir el presupuesto de uno activo y al activar lo existente, hasta fin de mes); y el **freno** `enforceMonthlyCaps` (cada vuelta del worker, antes de sincronizar) pausa los ACTIVE de la cuenta cuando el gasto del mes ≥ tope y anota en `AdPromotion.error` (auditoría `ads.paused_by_cap`); no frena lo activado directamente en Meta (para eso, el límite de gasto de la cuenta de Meta). El formulario de topes de Cuentas es `spend-caps-form.tsx` (`setSpendCapsAction`: un campo vacío quita ese tope; el mensual no puede ser menor que el diario); `activatePromotion` lo vuelve a comprobar con el presupuesto que Meta tiene en ese momento; para lo ya existente (`existing.ts`) cuenta la **suma** de lo que pueden gastar los conjuntos y los presupuestos totales (lifetime) no se activan desde la app. (4) Permisos: `ads.create` (ADMIN, EDITOR: crear y pausar) y `ads.approve` (ADMIN, APPROVER: activar, presupuesto, archivar); las funciones de `service.ts`/`manage.ts` **no** comprueban permisos, lo hacen las acciones de `anuncios/actions.ts` (que solo exporta acciones). (5) **Meta v26** (todo lo que depende de nombres está en `mapping.ts`): `special_ad_categories: []` obligatorio, `is_adset_budget_sharing_enabled: false`, `targeting_automation.advantage_audience` **siempre explícito en 0** (con 1 Meta trataría edad/género/intereses como sugerencias), intereses en `flexible_spec`, sin el placement «Explorar» de Instagram, `optimization_goal` por objetivo (ODAX), países/ciudades de la UE bloqueados (exigen DSA); impulsar Facebook = `object_story_id`, Instagram = `object_id`+`instagram_user_id`+`source_instagram_media_id` (y `publisher_platforms: ["instagram"]`); anuncio nuevo = `object_story_spec` (link_data o photo_data) con la imagen subida por `adimages` (hash); si Meta pide decidir sobre «Standard Enhancements» se reintenta con `degrees_of_freedom_spec` en OPT_OUT. **Las combinaciones solo se probaron con el simulador** y lo primero que dijo la cuenta real (2026-10-16) fue: (a) presupuesto mínimo en español («debe ser de más de $ 3.322») y (b) **la app de Meta debe estar en modo «Publicado» (Live) para crear anuncios** (código 100, subcódigo 1885183: «La publicación con contenido publicitario se creó con una app que se encuentra en modo de desarrollo»); `classifyAdsError` y `failureHints` los reconocen y el Manual (sección 8, paso «La app de Meta en modo Publicado») lo explica. Antes el Manual decía que en modo desarrollo funcionaba con las cuentas propias: era falso para crear anuncios. Ante otro rechazo de Meta el mensaje trae «Detalle de Meta» y se ajusta `mapping.ts`. (6) La duración cuenta **desde que se activa** (`end_time` exacto al activar; al crear solo uno provisional). El worker (`syncDuePromotions`) relee el estado real (`statusFromMeta`) y da por fallidas las creaciones interrumpidas. (7) UI: el formulario viaja entero como JSON en un campo (`payload`) y se valida con las mismas funciones puras que el servidor; **no uses `useMemo` manual** (el lint del compilador de React lo rechaza: `preserve-manual-memoization`); **no uses `<span class="sr-only">` dentro de una tabla con scroll** (un elemento absoluto escapa del recorte y ensancha toda la página en móvil: usa `aria-label`); los avisos de éxito de una acción desaparecen cuando cambia el estado y se desmonta el botón (las pruebas esperan el estado real, no el aviso) y Next trae su propio `role="alert"` vacío (las pruebas esperan uno con texto). **Un anuncio `FAILED` no se «reintenta» ni se reutiliza**: queda como historial (no quedó nada en Meta) y «Crear de nuevo» (`/anuncios/nuevo?copiar=<id>`, lista y ficha) abre el formulario con sus datos (`initial` de `PromotionForm`; la publicación de origen se agrega a las opciones aunque sea más vieja que las 60 recientes) y crea un anuncio **nuevo** que pasa todas las protecciones otra vez; `failureHints()` (`promotions/hints.ts`, puro) traduce el error a qué corregir; «Descartar» (aprobador) lo archiva sin tocar Meta. Meta responde en el idioma de la persona: `classifyAdsError` reconoce «debe ser de más de $ 3.322» como presupuesto mínimo. Pruebas: `tests/promotions-*.test.ts`, `tests/meta-marketing.test.ts`, `e2e/promotions.e2e.mjs`; el simulador `e2e/fake-meta-ads.mjs` exige lo que exige Meta (escenarios `adsFail`, `adsBudgetFactor` —100 simula una conversión de moneda mal hecha—, `adsReview`, `adsEnhancements`, `adsMinBudget`; `fake.ads.seed()` crea campañas «hechas en Meta»). **Recomendaciones de días** (`promotions/timing.ts`, puro y probado; `anuncios/timing-advice.tsx`, mismo componente en Crear anuncio y en la sección #recomendaciones del Manual): las fechas próximas (quincenas 15/30 adelantadas al viernes si caen en fin de semana, Madre, Padre, Amor y Amistad, Black Friday, Cyber Lunes, primas) se **calculan** desde «hoy» en `APP_TIMEZONE`, no se escriben a mano; los consejos por día de la semana son reglas generales (`AUDIENCE_TIPS`), no datos de la cuenta. Manual: sección #anuncios y comprobación `anuncios` del diagnóstico.
- **Estadísticas de las publicaciones** (`src/lib/stats/`, `src/lib/meta/post-metrics.ts`, `src/app/(app)/estadisticas/`, tabla `PostTargetMetrics`, migración `stats_metrics`): solo para lo publicado **desde la app** (`PostTarget` `PUBLISHED` con `externalId`), nunca para lo que alguien suba a mano. Una fila por destino con la última lectura: `views, reach, likes, comments, shares, saves` (`null` = la red no la entregó, que **no es 0**; solo Facebook omite `shares` cuando nadie compartió y ahí sí son 0), `fetchedAt` (última lectura buena), `nextFetchAt` y `note` (lo que no se pudo leer). **Meta cambia sus métricas cada pocos meses** (en 2025 retiró «impresiones» y puso «vistas»/«alcance»; los nombres de hoy se tomaron el 2026-10-16 de las páginas «Instagram Media Insights» y «Deprecated Metrics» del Pages API en developers.facebook.com) así que `post-metrics.ts` es tolerante a propósito: Facebook lee de la publicación `shares` (`pages_read_engagement`) y, **si tiene `pages_read_user_content`**, `reactions.summary` y `comments.summary` (son contenido de terceros: **sin ese permiso Meta rechaza TODA la lectura con «(#10) This endpoint requires the 'pages_read_user_content' permission or the 'Page Public Content Access' feature»; error real visto en la primera lectura con una cuenta de verdad, 2026-10-16**). Sin el permiso (`STATS_SCOPE.FACEBOOK_PAGE.content`; se sabe de antemano por `SocialAccount.scopes`, y si no se conocen se descubre con ese error y se reintenta solo `shares`) las reacciones salen del desglose `post_reactions_by_type_total` de los insights (se suma) y los comentarios quedan en `null` con aviso (las interacciones no los incluyen). Vistas/alcance salen de `/{id}/insights` con `post_media_view` y `post_total_media_view_unique` (`read_insights`); Instagram lee `like_count`/`comments_count` (`instagram_basic`) y `reach,views,saved,shares` de insights (`instagram_manage_insights`). Si Meta rechaza una métrica por inválida (código 100 que no sea «objeto no existe»), `readMetrics` pide las demás **de a una** y avisa cuál faltó; permisos o límites de uso en insights no tumban lo básico; solo un token vencido (190) se relanza. **Si Meta vuelve a renombrar métricas, se cambian solo los nombres de `fetchFacebookPostMetrics`/`fetchInstagramMediaMetrics` y `METRIC_NAMES`**; no están verificadas con una cuenta real (la app del usuario aún no publica de verdad). `refresh.ts`: `refreshDueMetrics` (en cada vuelta del worker, **al final y con tope de 20 s** para no retrasar publicaciones) toma destinos sin lectura o con `nextFetchAt` vencido (cuenta `ACTIVE`, últimos 90 días, 6 por vuelta); calendario `nextFetchAfter` (3 h los 2 primeros días, 12 h hasta 14, diario hasta 90, luego ya no) y `retryAfterFailure` (red 30 min, límite de uso 2 h, conexión vencida 1 h, permisos/otros 12 h, «no existe» 24 h). Un fallo **conserva las cifras anteriores** (`mergeMetrics`; solo anota `note`/`nextFetchAt`); un token vencido deja la cuenta `EXPIRED` como al publicar. Los permisos concedidos se miran antes (`missingStatsScopes` en `meta/scopes.ts`): sin el básico no se llama a Meta; sin el de insights solo se pide lo básico. «Actualizar» (`stats.refresh`: ADMIN, EDITOR, APPROVER; `actions.ts`) relee las 12 más recientes del filtro, saltando las leídas hace menos de 2 min. Resumen en `metrics.ts` (`summarize`): el alcance **no se suma** entre publicaciones (se muestra el medio) y la tasa pondera interacciones totales / alcance total solo con las que tienen ambas. La pantalla usa `metrics.view` (todos los roles); sus tablas llevan `aria-label` (las pruebas las localizan por él). Manual: sección `#estadisticas` y comprobación `estadisticas` en el diagnóstico; ficha de la publicación resume las cifras de cada destino. Pruebas: `tests/stats-*.test.ts`, `tests/meta-post-metrics.test.ts`, `e2e/stats.e2e.mjs` (el Meta simulado calcula las cifras del número final del id: `P-1_10` → n=10; escenarios `stats: noinsights|nousercontent|badmetric|ratelimit|gone|hidelikes` y `statsBoost`). **Lección:** el primer fallo real vino de un permiso que la documentación no dejaba claro y que el simulador no modelaba; al agregar una lectura nueva a Meta, pide cada cosa que pueda exigir un permiso distinto por separado o prevé qué guardar si esa parte falla, y súmalo al simulador con el error literal de Meta.
- **Fase 4, anuncios de varias plataformas** (`src/lib/ads/`, `src/lib/google/`, `src/lib/tiktok/`): cada plataforma aporta un `AdsConnector` (`ads/types.ts`: `configError`, `fetchInsights`, `classifyError`) y todo lo demás es común en `ads/sync.ts` (`syncAdAccount` para cualquier plataforma: fechas en la zona de la cuenta, `replaceInsights` en una transacción con `timeout: 60_000`, estado de la cuenta, `EXPIRED` si el conector dice que la conexión murió) y `ads/save.ts` (`saveAccounts`: findMany + createMany + updateMany concurrentes, una cuenta mala va a `skipped`; Meta también lo usa). `ads/lock.ts` impide sincronizar la misma cuenta dos veces a la vez en un proceso (worker + botón) porque dos `replaceInsights` simultáneos pueden dar deadlock. `ADS_PLATFORM_IDS`/`isAdsPlatform` están en `platforms.ts` (puro, usable en cliente). **Google Ads**: OAuth web con `access_type=offline` + `prompt=consent` (sin eso no hay token de renovación) y scope `adwords` (+ `openid email` solo para mostrar con qué correo se conectó); **en modo «Prueba» del consentimiento el token de renovación caduca a los 7 días** (hay que pasar a «En producción»); el token de acceso dura 1 h: se renueva en `accessTokenFor` con caché en memoria por token de renovación (una renovación por hora para todas las cuentas de la misma conexión) y su vencimiento va en `SocialAccount.metadata.accessExpiresAt` (NO en `tokenExpiresAt`: la pantalla Cuentas lo mostraría como «conexión vencida» cada hora). Desde 2026-09-09 el `developer-token` es opcional e ignorado: el acceso lo da el proyecto de Google Cloud (Explorer/Básico/Estándar; un proyecto nuevo con solo acceso de prueba da `CLOUD_PROJECT_NOT_APPROVED_FOR_PRODUCTION` con cuentas reales). REST `googleAds:searchStream` con GAQL (la respuesta es un arreglo de lotes, JSON en camelCase, enteros de 64 bits como texto, `costMicros` → decimal con BigInt sin coma flotante); las cuentas cliente de una MCC se consultan con la cabecera `login-customer-id` (se guarda en `metadata.loginCustomerId`); la MCC en sí no se guarda y el acceso directo manda sobre el de la MCC. `invalid_client` llega como 401 pero **no** es una conexión vencida (es el `.env`): `GoogleApiError.isAuthError` lo excluye. El `tsconfig` apunta a un target anterior a ES2020: nada de literales BigInt (`1n`), usar `BigInt(1000000)`. **TikTok**: Marketing API v1.3, token en la cabecera `Access-Token`, **responde HTTP 200 con errores (manda `code`)**, `code` 40105/40104 = token inválido, 40100/40016/40133 = límite de uso; el token no vence solo (sin renovación); los reportes diarios no pueden pasar de 30 días por consulta (`dateChunks`) y vienen paginados; datos con ~11 h de retraso. La documentación de TikTok no es legible por herramientas: los endpoints se contrastaron con conectores de terceros, validar con una app real. Anuncios y Cuentas aceptan las tres plataformas; `buildReport` devuelve `platforms` (desglose por plataforma dentro de cada moneda) y las monedas distintas nunca se suman. Eventos de auditoría: `meta|google|tiktok.{connected,synced,disconnected,connect_denied,connect_rejected,connect_failed}` y `ads.synced_all`. Pruebas: `e2e/fake-google.mjs` y `e2e/fake-tiktok.mjs` (`GOOGLE_OAUTH_BASE_URL`, `GOOGLE_ADS_API_BASE_URL`, `TIKTOK_API_BASE_URL`, solo localhost) con cifras deterministas; `npm run test:e2e:ads` arranca tres instancias (con credenciales, sin ellas y con el worker encendido).
- **Fase 3, publicaciones** (`src/lib/post-workflow.ts`, `src/lib/publishing/`, `src/lib/meta/publish.ts`, `src/lib/worker.ts`, `src/app/(app)/publicaciones/`): una sola máquina de estados (`DRAFT → IN_REVIEW → APPROVED → SCHEDULED → PUBLISHING → PUBLISHED|PARTIAL|FAILED`, más `CANCELLED`) que consultan pantallas y acciones. Cada acción de `[id]/actions.ts` comprueba permiso + estado permitido + `validatePostForReview` y cambia el estado con un `updateMany` condicional (dos personas a la vez no se pisan). **El worker** arranca desde `src/instrumentation.ts` (una vez, `globalThis.__redesWorker`; `WORKER_ENABLED`, `WORKER_INTERVAL_SECONDS`) y `runDuePublications` reserva cada `PostTarget` con `updateMany` condicional: dos procesos (worker + `after()` de «Publicar ahora», o dos copias de la app) nunca publican lo mismo. Un destino `PUBLISHING` con más de 10 min pasa a `FAILED` («revisa en la red social») y **no se reintenta solo**: repetirlo a ciegas duplicaría la publicación. Fallos temporales reintentan a los 2/10/30 min (4 intentos); los definitivos (permisos, token vencido → cuenta `EXPIRED`, imagen rechazada) no. «Reintentar» solo toca destinos `FAILED`. **Permiso de publicar**: `SocialAccount.scopes` guarda lo que Meta concedió en la conexión; `src/lib/meta/scopes.ts` (`missingPublishScope`) lo compara con `pages_manage_posts` / `instagram_content_publish` y se aplica en `validatePostForReview` (enviar/aprobar/programar/publicar/reintentar), en `publishOne` (falla sin llamar a Meta) y en la pantalla Cuentas; con `scopes` nulo o vacío no bloquea. Caso real del usuario (2026-10-16): `META_SCOPES` solo traía anuncios y páginas, por eso las 4 páginas conectadas no podían publicar y no había Instagram. El error de permisos de Meta incluye ahora su texto («Detalle de Meta: (#200)…»). **Instagram descarga la imagen por URL**: `publicMediaUrl()` exige HTTPS público (`APP_URL` o `MEDIA_PUBLIC_BASE_URL`) y avisa antes de llamar a Meta; `/media/[key]` es público solo con la publicación `SCHEDULED|PUBLISHING|PUBLISHED|PARTIAL`. Instagram solo acepta JPG: `media-uploader.tsx` convierte los PNG a JPG **en el navegador** (canvas, fondo blanco, calidad 0,95) antes de subirlos; si no puede, sube el original y el servidor lo valida igual (la validación por contenido y `validatePostForReview` siguen mandando). **Varias imágenes por publicación** (`MAX_IMAGES_PER_POST = 10` en `media-format.ts`, el tope del carrusel de Instagram; `PostMedia.position` ya existía, sin migración): `PublishInput.images` va en orden (la primera es la portada). Facebook: con 1 imagen `/photos` con pie como siempre; con 2+ cada foto se sube con `published=false` (sin pie) y luego **un solo** `/feed` con `attached_media[i]={"media_fbid":…}` (el enlace va dentro del texto, esa llamada no lleva `link`). Instagram: con 1 imagen igual que antes; con 2+ un contenedor hijo por imagen (`is_carousel_item=true`, sin pie), se espera a cada uno, un padre `media_type=CAROUSEL` + `children` (el pie va aquí) y se publica el padre. Un reintento tras un fallo vuelve a crear contenedores/fotos sin publicar (inofensivos); lo que no cambia es que un destino `PUBLISHING` colgado no se reintenta solo. `validatePostForReview` revisa cada imagen para Instagram («Imagen 2: …») y el máximo; subir es de a una por `POST /api/posts/[id]/media` (la posición es la última + 1, el navegador las manda en orden) y `moveMedia` (acción) intercambia con la vecina. **La regla de que Instagram recorta todas con la proporción de la primera sale de una guía de terceros, no de la documentación de Meta; el límite real de fotos por publicación de Facebook no está verificado** (se usa 10). Los anuncios usan solo `media[0]`. Probado solo con el Meta simulado (`photo-unpublished`, `feed.attached`, `ig-child`, `ig-carousel`). Las imágenes viven en `MEDIA_DIR` (disco, no BD): entran en las copias de seguridad. **Son por servidor, la BD puede ser compartida**: dos copias de la app contra la misma BD (p. ej. el PC del usuario y el VPS) solo ven los archivos que subieron ellas, y en Docker/Easypanel sin un Volume en `/data/media` se pierden al redesplegar (le pasó al usuario el 2026-10-16: «No se encontró el archivo de la imagen en este servidor»). `MISSING_IMAGE_MESSAGE` (media.ts) explica la causa; el diagnóstico `archivos` del Manual cuenta cuántas de las últimas 100 imágenes registradas faltan en este servidor (`imageExists`). **Restaurar** (`POST /api/posts/[id]/media/[mediaId]`, `restore-image.tsx`): solo si el archivo de verdad falta, solo en publicaciones `PUBLISHED`/`PARTIAL` (lo aprobado/programado no se cambia por esta vía) y la imagen nueva debe medir exactamente `width × height` de la registrada; renombra la clave de almacenamiento y audita `post.media_restored`; el formulario de «Anuncio nuevo» detecta `imageMissing` y manda a la publicación. Una opción de fondo, si vuelve a pasar, es guardar las imágenes en la BD o en almacenamiento de objetos. Las rutas de `media.ts` llevan `/*turbopackIgnore: true*/` (si no, el build avisa de que traza todo el proyecto).
- **IA, varios motores** (`src/lib/ai/`): Claude, GPT (OpenAI) y Gemini (Google) detrás de una interfaz `Engine` (`engines/types.ts`: `run()` y `listModels()`, **nunca lanzan**: devuelven un mensaje en español). `generate.ts` es independiente del proveedor: arma los prompts (`prompts.ts`), llama al motor, valida el JSON con zod y aplica las reglas de la marca (palabras prohibidas descartadas en el servidor, hashtags, límites). Claude usa `@anthropic-ai/sdk` (`client.beta.messages.create`, `output_config` con `json_schema` y `effort`, `fallbacks: "default"` + cabecera beta `server-side-fallback-2026-07-01` con reintento sin ella, perfil de marca en `system` con `cache_control`, `stop_reason`). OpenAI y Gemini van por `fetch` (`engines/http.ts`: reintenta 429/5xx/red, `retry-after-ms`, sin registrar URL ni cabeceras): OpenAI = Responses API (`POST /v1/responses`, `text.format` json_schema estricto, si el modelo se queja del formato reintenta en `json_object` con la forma descrita, `store:false`); Gemini = `generateContent` con la clave en `x-goog-api-key` (nunca en la URL; Google responde **400**, no 401, a una clave mala), `responseMimeType: application/json`, tokens de «pensar» cuentan como salida. No se manda `reasoning`/`effort` a OpenAI ni Gemini (los modelos que no lo soportan lo rechazan). **Los nombres de modelo cambian cada pocos meses**: el modelo de cada motor es configurable y `listModels()` (botón «Cargar modelos») pregunta a la API qué ve la clave; los de `catalog.ts` (`gpt-6.1-sol`, `gemini-3.8-flash`, `claude-opus-5-5`) son solo la propuesta inicial, tomados de la documentación oficial el 2026-10-15. Las claves las pone un administrador en `/ia` (permiso `ai.manage`, solo ADMIN) y se guardan **cifradas** en la tabla `AiProvider` (`apiKeyEnc` + `keyHint` con los últimos 4); `providers.ts` es el único sitio que las descifra, las páginas leen solo el estado (`providers-core.ts`, lógica pura y probada). `ANTHROPIC_API_KEY` del `.env` sigue valiendo como respaldo de Claude; la clave guardada en la app manda. El motor pedido que ya no está disponible **no se sustituye en silencio** (error). Límite diario por persona (`AI_DAILY_LIMIT`, tabla `AiGeneration` con `provider`) compartido entre motores. Las claves se quitan de cualquier mensaje con `redactKey()`. Pruebas: `e2e/fake-{anthropic,openai,gemini}.mjs` (`ANTHROPIC_BASE_URL`, `OPENAI_BASE_URL`, `GEMINI_BASE_URL`; las dos últimas solo aceptan localhost). Para sumar un proveedor: un archivo en `engines/` + su entrada en `catalog.ts` y `engines/index.ts`.
- **`"use server"` solo exporta acciones**: cualquier función exportada de un archivo `actions.ts` queda como endpoint público; no exportes ayudas ahí (están en `providers.ts`).
- **Zonas horarias**: en BD todo es UTC (Prisma). Las horas de una publicación programada se escriben y muestran en la zona de **su marca** (`src/lib/time.ts`, DST-aware). Cualquier otra fecha en pantalla usa `dateTimeFormat()` (`src/lib/display-time.ts`, `APP_TIMEZONE`, por defecto `America/Bogota`): **nunca** `new Intl.DateTimeFormat("es", …)` sin `timeZone` en una página de servidor, porque el VPS suele estar en UTC y las horas saldrían corridas. En SQL a mano usa `UTC_TIMESTAMP()`, no `NOW()`.
- **`src/proxy.ts`**: sin cookie, las navegaciones van a `/login` y las llamadas de datos (`/api/*` que no son GET) reciben 401 JSON; un redirect 307 reenviaría el POST a `/login` y Next lo intentaría leer como formulario (error 500).
- **Pruebas e2e de contenido**: `test:e2e:content` (marcas + IA) y `test:e2e:pipeline` (recorrido completo con worker, reintentos, calendario, dos procesos compitiendo, apps arrancadas con `TZ=UTC`). Trampas ya vistas al escribirlas: tras una acción que cambia el estado, la página se vuelve a dibujar y el aviso de éxito desaparece (comprobar en la BD, no en el aviso); con el worker encendido, una publicación vencida a medio crear se publica incompleta (poner `scheduledAt` al final); `multipart/form-data` normaliza `\n` a `\r\n`; `aside` es ambiguo (el menú lateral también lo es: usar `main aside`); los datos del calendario van en el mes siguiente para no mezclarse con lo que la prueba crea hoy.
- **La base de datos de producción está lejos (~0,2 s por consulta)**: nada que dependa de varias consultas puede ir en una sola `$transaction` con límite de 5 s ni en `upsert` por fila (cada `upsert` de Prisma son varias idas y vueltas). `saveMetaConnection` hace `findMany` + `createMany` + `updateMany` concurrentes, y `replaceInsights` usa una transacción interactiva con `timeout: 60_000`. Una cuenta que falla al guardarse queda en `skipped` (con el motivo vía `describeInternalError`, visible en la actividad de Equipo) y no tumba la conexión. Lo comprobó un experimento con latencia simulada: el guardado antiguo falló con *"transaction timeout 5000 ms"* y el nuevo tarda ~2 s con 36 cuentas. `E2E_DB_LATENCY_MS=100 npm run test:e2e:meta` repite la prueba con la base lenta; úsalo al tocar código que escribe muchas filas.
- **Prisma 7**: `migrate dev` ya no regenera el cliente; tras cambiar `schema.prisma` ejecuta `npx prisma generate`. **Las migraciones generadas en Windows salen con `ALTER TABLE \`nombre_en_minusculas\``**: en el VPS (Linux) los nombres distinguen mayúsculas, así que hay que corregirlas a mano (`SocialAccount`) antes de desplegar y comprobar que aplican limpias en una base nueva.
- **Formato de monedas** (`src/lib/format.ts`, `spend-chart.tsx`): no forzar decimales; cada moneda trae los suyos (COP 0, USD 2). Un periodo "hoy" se calcula en la zona horaria de la cuenta, no en la del servidor ni UTC.
- **Docker / Easypanel** (`Dockerfile`, `docker-entrypoint.sh`, `.dockerignore`, `.gitattributes`): imagen `node:22-bookworm-slim` en dos etapas; el `.env` nunca entra (`.dockerignore`). `next build` falla sin `DATABASE_URL` (`src/lib/db.ts` llama a `env()` al importarse y Next importa las rutas al compilar; comprobado construyendo sin `.env`), por eso el `RUN npm run build` lleva una URL de relleno solo en ese comando. **No usa `output: "standalone"` a propósito**: el arranque corre `prisma migrate deploy` (CLI de Prisma = devDependency), así que la etapa final copia toda la app con `node_modules`. El entrypoint arranca como root solo para `chown` de `MEDIA_DIR` (un volumen montado llega como root) y se baja a `node` con `setpriv` (reemplaza el proceso: las señales de parada llegan a Next); `RUN_MIGRATIONS=false` salta las migraciones; `docker-entrypoint.sh` debe quedar con LF (`.gitattributes`; el Dockerfile además le quita los CR). El healthcheck pide `/login` (pública). Nunca se ha construido con Docker real (no hay Docker en el PC de desarrollo): la primera construcción en Easypanel es la prueba.
- **Lint**: `react-hooks/purity` prohíbe `Date.now()` directo en componentes; usa una función auxiliar a nivel de módulo.

## Comandos

```
npm run dev | build | start
npm run typecheck && npm run lint && npm test
npm run db:migrate        # desarrollo: crea/aplica migraciones
npm run db:deploy         # producción: aplica pendientes
npm run test:e2e          # Fase 1, navegador real; vacía la base *_test (ver README)
npm run test:e2e:meta     # Fase 2, arranca app + Meta simulado; exige `npm run build` previo
npm run test:e2e:content  # Fase 3a, marcas + IA con Claude simulado
npm run test:e2e:pipeline # Fase 3b/3c, publicación completa con Meta simulado
npm run test:e2e:engines  # varios motores de IA (Claude/GPT/Gemini), 3 servidores simulados
npm run test:e2e:ads      # Fase 4, Google Ads + TikTok Ads con servidores simulados
npm run test:e2e:stats    # estadísticas de las publicaciones (worker + Meta simulado con fallos)
npm run test:e2e:promotions # anuncios desde la app (tope, pausa, aprobación, protección del dinero)
```

Antes de dar una fase por hecha: typecheck, lint, unit tests, `npm run build` (sin avisos), `test:e2e`, `test:e2e:meta`, `test:e2e:content`, `test:e2e:pipeline`, `test:e2e:engines`, `test:e2e:ads`, `test:e2e:stats` y `test:e2e:promotions` en verde, y revisar capturas (claro, oscuro, móvil) de las pantallas nuevas (`E2E_SHOTS_DIR`).
